# Publication snapshot contract

A production snapshot is a complete public data tree. It contains `catalog.json`, each referenced episode's `detail.json` and bilingual VTT files, reviewed cover assets, `feed.xml` and `feed-en.xml`. The catalog/detail schemas remain v1 in `packages/catalog`. No source recordings, generated MP3 files, internal manifests, configuration, caches, executable files or workflow definitions belong in a snapshot.

## Build and validation

`build_publication.py` exports newly verified episodes and can merge an earlier verified snapshot. The earlier snapshot is the durable public-content ledger: its articles, captions and audio URLs survive removal of large local processing files. Freshly completed episodes replace the same ID; other archived episodes remain. Production ledgers reject reference previews. Unknown video/source groups use the bilingual metadata in `site/other-series.json`.

The Node snapshot copier reads only schema-approved catalog/detail/caption paths. It rejects symlinks, including aliases within the input directory. It ignores all other input files. Covers are copied from the reviewed source `site` directory, never from the untrusted data snapshot. Referenced covers must remain available there. It validates the complete copied output, including exact VTT/timeline agreement. This is also the intended boundary for a later Pages data-branch loader; data cannot replace app HTML, JavaScript, workflows or the brand asset.

The builder assembles and validates private staging, renders RSS, then renames the completed directory into a fresh output path. Failure leaves an existing publication untouched. It never uploads assets, pushes Git, updates a persistent ledger pointer or deletes processing files. The publishing transaction must do those steps separately, after remote asset verification and successful site deployment.

## Bilingual RSS

Feed text is stored in `site/feed-dict.json`; episode titles/summaries use their reviewed locale values. English metadata never falls back to Chinese. Both feeds explicitly disclose synthetic narration and contain only verified podcasts. The audio language remains Mandarin in both feeds. Owner email is optional and accepts only the project's public noreply format.

Each episode/audio hash pair has a content-version GUID. Updating the recording therefore changes both the immutable enclosure URL and its GUID. Unchanged catalog content retains `generatedAt`, so repeat builds produce stable catalog and RSS bytes. Dates and ordering use UTC with deterministic ID ordering for ties.

```sh
pnpm moon run pipeline:publication -- \
  --output /tmp/babel-new-publication \
  --previous /srv/babel/publications/verified-snapshot \
  --site-url https://example.github.io/babel \
  --audio-base https://github.com/example/babel/releases/download/audio
```

Omit `--previous` for the first production snapshot. `--author` and an optional public `--email` supply publishing attribution. Feed titles and descriptions are localized in the dictionary. Episode source/model/text/audio provenance is preserved from the verified catalog. The current legacy publisher is not switched by this build-tool change.

## Pages data boundary

The Pages workflow runs only for main. Application code is checked out at the immutable main event SHA. An optional `publication_revision` input must be a complete lowercase commit SHA and is used only for a separate `.publication-input` checkout. Without that input, the resolver reads `refs/heads/publication`; a genuinely absent branch is the initial reference-preview state. Git/network failures stop deployment rather than using that fallback.

The trusted snapshot builder rebuilds this data into private staging with the current code's covers, dictionaries and feed rendering. Only that validated output replaces Web public data; the reviewed brand and application source stay separate. Web builds do not use cached output because externally supplied article/caption data can change independently of source commits. The normal public artifact validator runs before upload.

`publication.json` is generated by reviewed build code. It contains `codeRevision`, `dataRevision` (null for the initial preview), the SHA-256 of the final catalog and the public workflow run ID. A future publisher must verify this receipt before advancing its durable ledger or removing large processing files. It does not contain server identity or credentials.

Public repository variables `SHOW_AUTHOR`, optional noreply `SHOW_EMAIL` and canonical Ko-fi `VITE_SUPPORT_URL` supply attribution/support settings. They are public presentation data, not secrets. Build jobs retain contents-read access; Pages/OIDC write permissions remain isolated in the deploy job.

## Asset publication and ledger

`publish_assets.py` stages verified episode audio without uploading anything. Each staged file is named exactly like the catalog enclosure basename, `<episode-id>-zh-<audioSHA256[:12]>.mp3`, so a file dropped into the `audio` release matches the immutable URL the catalog already publishes. The name is deterministic: the same verified version stages under the same name on every run, and any content change changes the embedded hash.

`manifest.json` records, per episode ID, the staged file name, byte SHA-256, byte count, duration and the catalog content version (the full verified `audio_sha256`; the RSS GUID is `<episode-id>-zh-<contentVersion>`). Staging copies only episodes that pass the single publication gate; missing or unverified audio is skipped, and staged bytes are re-hashed against `speech.json` before the manifest is written. `verify_staging` recomputes every digest and rejects a manifest whose ID, content version and file name do not agree, so a tampered staging directory fails before any upload.

```sh
pnpm moon run pipeline:assets -- --output /srv/babel/assets/staging
```

The durable ledger is `ledger.json`, an asset of the public `audio` release next to the audio files: durable with the release, publicly verifiable, and readable by the daily scheduler without extra state. Its `episodes` map records, per episode ID: content version, asset file name, byte SHA-256, byte count, first-published timestamp and the source snapshot `dataRevision` (null for the initial preview). `plan_uploads` compares a ledger with a fresh manifest and returns `new` and `unchanged` IDs; the same ID with a different byte SHA-256 is content drift and raises — a publisher must never overwrite a released asset. Entries survive pruning of heavy local caches: episodes absent from a later manifest stay in the ledger and are not re-uploaded.

`advance_ledger` gates on the publication receipt: `verify_receipt` requires `publication.json`'s `catalogSha256` to match the staged `catalog.json` bytes, with `dataRevision` null or a full lowercase commit SHA, before any new entry is added. Only the private publishing workflow, after remote asset verification and successful site deployment, uploads staged files to the `audio` release and stores the advanced ledger; this public tool never uploads, pushes Git, advances a remote ledger pointer or deletes processing files. The current legacy publisher is not switched by this build-tool change.
